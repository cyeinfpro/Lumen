## 3. 已确认 Bug

## IMG-20260913-01：合法的 Agent `null` 响应在 validator 前被拒绝

**等级：P1 / High**

### 3.1 涉及文件

- `apps/api/app/routes/agent_sessions.py:214-228`
- `apps/web/src/features/agent/api/agentApi.ts:170-179`
- `apps/web/src/features/agent/api/validators.ts:628-635`
- `apps/web/src/lib/api/response.ts:18-50`
- `apps/web/src/lib/api/transport.ts:116-136`
- `apps/web/src/features/agent/containers/AgentWorkspaceController.tsx:205-232`
- `apps/web/src/features/agent/containers/useAgentSnapshotPolling.ts:22-53`
- `apps/web/src/lib/api/apiTransport.test.ts:65-150`
- `apps/web/e2e/agent-fixture.ts`（mock 已会对无活跃任务会话返回 `null`，但缺少契约断言）

### 3.2 服务端契约

后端明确声明该接口允许没有活跃任务：

```python
@router.get(
    "/sessions/{session_id}/active-run",
    response_model=AgentRunOut | None,
)
async def get_agent_active_run(...) -> AgentRunOut | None:
    return await get_active_agent_run_snapshot(...)
```

因此，新会话、空闲会话、已完成任务的会话返回：

```http
HTTP/1.1 200 OK
Content-Type: application/json

null
```

属于正常成功响应，不是异常数据。

### 3.3 前端也声明允许 `null`

API 类型和 validator 均明确接受 `null`：

```ts
export function getAgentActiveRun(...): Promise<AgentRun | null> {
  return apiFetch<AgentRun | null>(
    `/agent/sessions/${encodeURIComponent(sessionId)}/active-run`,
    { signal, validate: validateNullableAgentRun },
  );
}

export function validateNullableAgentRun<T>(value: unknown): T {
  if (value === null) return value as T;
  return parseAgentRun(value, "/agent/sessions/active-run") as T;
}
```

### 3.4 实际冲突点

公共成功响应解析器在 validator 之前无条件拒绝 JSON `null`：

```ts
const data = await res.json();
if (data === null) {
  throw new ApiError({
    code: "response_schema_error",
    message: "Successful typed API response contains JSON null",
    status: res.status,
    ...
  });
}
```

`ApiTransport.request()` 的顺序是：

```ts
const data = await readSuccessResponseData(response);
return validate
  ? applyResponseValidator(response, path, data, validate)
  : (data as T);
```

所以 `validateNullableAgentRun()` 永远收不到 `null`。

### 3.5 正常触发路径

1. 用户新建、打开或切换到一个没有正在运行 Agent Run 的会话。
2. `GET /agent/sessions/{id}/active-run` 返回 `200 application/json` 和 `null`。
3. `readSuccessResponseData()` 抛出 `response_schema_error`。
4. `useAgentActiveRunQuery()` 进入错误状态，并按 React Query 默认行为重试或在聚焦时再次请求。
5. `refreshSnapshot()` 使用：

   ```ts
   const [snapshot, run] = await Promise.all([
     listAgentMessages(...),
     getAgentActiveRun(...),
   ]);
   ```

   active-run 一侧失败会让整个 `Promise.all()` 拒绝；即使消息列表请求成功，本次消息快照也不会被应用。
6. `useAgentSnapshotPolling()` 捕获该异常并把实时状态设为 `error`，后续定时、窗口聚焦和 SSE 触发的协同恢复仍会重复失败。

### 3.6 用户可见影响

- 空闲 Agent 会话的 active-run 查询持续报错。
- 协同快照刷新被连带阻断，消息、任务和图片状态的兜底恢复不能正常完成。
- SSE 短暂断开后，本应依赖 snapshot 恢复的状态可能长时间停留在旧值。
- 轮询会反复进入 `error`，产生额外请求和噪声日志。
- E2E fixture 已能返回此正常 `null`，但现有测试只覆盖页面主行为，没有断言 transport 无错误或实时状态不进入 `error`，因此问题长期未被发现。

未发现该问题会直接造成重复扣费或服务端重复任务；其主要风险是 Agent 工作区状态恢复失效和错误状态持续化。

### 3.7 当前 HEAD 最小复现

本轮直接编译并执行当前 `apps/web/src/lib/api/response.ts`，输入：

```ts
new Response("null", {
  status: 200,
  headers: { "content-type": "application/json" },
})
```

结果：

```json
{
  "reproduced": true,
  "code": "response_schema_error",
  "status": 200,
  "validatorCalled": false,
  "message": "Successful typed API response contains JSON null"
}
```

关键证据是 `validatorCalled: false`：不是 nullable validator 写错，而是 transport 在 validator 之前截断了合法值。

全仓契约扫描同时确认：当前 `apps/api/app` 中唯一声明 `response_model=... | None` 的路由就是该 active-run 接口，因此当前修复范围明确，不需要大面积改动业务 API。

### 3.8 推荐修复

不要直接删除“默认拒绝 JSON `null`”的保护，否则未配置 validator 的普通 typed 请求可能静默接收错误响应。建议增加显式、默认关闭的 nullable response 契约。

#### `apps/web/src/lib/api/response.ts`

```ts
export interface SuccessResponseOptions {
  allowNull?: boolean;
}

export async function readSuccessResponseData(
  res: Response,
  options: SuccessResponseOptions = {},
): Promise<unknown> {
  if (res.status === 204) return undefined;
  const contentType = res.headers.get("content-type") ?? "";
  // 保留现有 content-type 与 JSON parse 校验
  const data: unknown = await res.json();
  if (data === null && !options.allowNull) {
    throw new ApiError({
      code: "response_schema_error",
      message: "Successful typed API response contains JSON null",
      status: res.status,
      payload: { content_type: contentType },
    });
  }
  return data;
}
```

#### `apps/web/src/lib/api/transport.ts`

```ts
export type TransportRequest<T = unknown> = RequestInit & {
  requestClass: RequestClass;
  budget?: RequestBudget;
  expectNoContent?: boolean;
  allowNullResponse?: boolean;
  applyCsrf?: boolean;
  validate?: ResponseValidator<T>;
};

async request<T>(path: string, init: TransportRequest<T>) {
  const {
    expectNoContent = false,
    allowNullResponse = false,
    validate,
    ...requestInit
  } = init;

  return this.requestRaw(
    path,
    requestInit,
    async (response) => {
      if (expectNoContent) return undefined;
      const data = await readSuccessResponseData(response, {
        allowNull: allowNullResponse,
      });
      return validate
        ? applyResponseValidator(response, path, data, validate)
        : (data as T);
    },
  );
}
```

同时把 `allowNullResponse?: boolean` 加入 `ApiFetchInit` / `QueryOptions` 类型，使其不会落入原生 `fetch` 参数。

#### `apps/web/src/features/agent/api/agentApi.ts`

```ts
return apiFetch<AgentRun | null>(
  `/agent/sessions/${encodeURIComponent(sessionId)}/active-run`,
  {
    signal,
    allowNullResponse: true,
    validate: validateNullableAgentRun,
  },
);
```

### 3.9 必须补的回归测试

1. 默认行为不变：普通成功响应 `200 null` 仍抛 `response_schema_error`。
2. `allowNull: true` 时 `readSuccessResponseData()` 返回 `null`。
3. nullable validator 必须被调用，并返回 `null`。
4. `getAgentActiveRun()` 对 `200 null` 返回 `null`，不重试、不报 schema error。
5. `refreshSnapshot()` 在 active run 为 `null` 时仍应用消息快照。
6. polling 不得把正常空闲会话设为 `error`。
7. Playwright：切换到 fixture 中返回 `null` 的 `session-2`，断言页面实时状态正常、控制台无 `response_schema_error`、消息刷新仍发生。

## 4. 条件性风险与建议测试

以下事项值得继续加固，但当前证据不足以列为已确认 Bug。

### 4.1 视频成功处理的跨提交窗口

`apps/worker/app/tasks/video_generation_parts/persistence.py` 会先提交 `RUNNING/FETCHING`，再下载、落对象存储、校验 artifact fence 并结算。当前已有 execution epoch、owner fence、取消复查和 reconciliation，未证明会双扣或错误采纳。

建议增加故障注入矩阵：

- 提交 FETCHING 后、下载前崩溃
- 对象写入后、DB adoption 前崩溃
- 取消与 adoption 并发
- reconciliation 重启后重复进入

断言最终只有一个已采纳 artifact、一次结算，孤儿对象可回收。

### 4.2 Provider quota reservation 的架构约束

当前图片 provider 的发送前 reservation 与失败释放链完整，未发现现有调用者绕过。但正确性依赖以后新增调用路径继续经过统一 facade。

建议增加架构测试，枚举所有 image provider dispatch 入口，强制断言调用 `_image_request_attempt_claim()`，并在异常、取消、超时、fallback 各路径检查 reservation 释放。

### 4.3 对象存储与数据库无法真正跨系统原子提交

当前通过 deterministic key、adoption probe、owner fence、延迟 sweep 降低风险。它属于系统边界，而非当前已证实数据错误。

建议做 chaos test：在“对象写入成功、DB commit 未知”“DB commit 成功、worker 未收到确认”等点注入进程终止，验证重试不会重复结算且 orphan sweep 不会删除已被新执行代次采纳的对象。

### 4.4 Canvas 跨标签页即时通知依赖 BroadcastChannel

不支持或创建失败时，不会收到即时跨标签页通知，但 revision 冲突和后续查询仍提供最终一致性。建议补 `storage` event 或可见性恢复时强制 revision refresh 作为兼容路径；当前未证明会导致持久数据丢失。

## 5. 已证伪并撤销的候选问题

深挖过程中对候选问题进行了当前 HEAD 反检查，以下不应继续作为 Bug 传播。

### 5.1 image-job 重试造成重复上游任务或重复费用 —— 不成立

- Worker 在 `apps/worker/app/upstream_parts/image_job_submission.py` 发送稳定 `Idempotency-Key`。
- Sidecar 在 `image-job/image_job/application/job_service.py` 强制校验该键，并按 owner、上游凭据、请求哈希去重。
- 同键不同请求会冲突；并发插入由唯一约束和 `IntegrityError` 后重读处理。

### 5.2 批量图片先按 N 张结算、后保存额外图片 —— 当前版本不成立

- `finalize_generation_success()` 先调用 `finalize_batch_extra_images()`。
- 额外图片逐张持久化并独立结算；无法证明落盘时会进入 takeover 恢复。
- 主图最终只以 `image_count=1` 结算。

### 5.3 Provider 统计刷 Redis 失败会覆盖并发新计数 —— 不成立

`flush_stats_to_redis()` 在锁内把快照交换为零，锁外执行 Redis pipeline；失败后再次锁定并使用 `+=` 合并旧快照。等待 Redis 时产生的新计数不会被覆盖。

### 5.4 `Retry-After` 不支持 HTTP-date —— 不成立

`apps/worker/app/http_retry.py` 已先解析秒数，失败后使用 `email.utils.parsedate_to_datetime()` 解析 HTTP-date，并检查有限值与负数。

### 5.5 钱包并发结算、兑换并发、密码重置双消费等历史候选 —— 当前调用链未成立

当前实现存在钱包行锁、加锁后幂等复查、消费记录守卫以及原子 `GETDEL` 等保护。没有用旧审计结论覆盖当前源码。
